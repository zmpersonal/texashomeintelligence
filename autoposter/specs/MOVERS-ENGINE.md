# MOVERS-ENGINE.md — the analysis layer (the actual product)

Everything else in this package is packaging. **This is the engine.** It sits between THI's raw
ingest and the one weekly caption call, and it answers the only question that matters: *which
area did the most interesting thing this week, and why.* It is 100% deterministic code — **zero
model tokens.** The model never decides what's interesting; this engine does, and hands the
caption call a pre-selected winner. Build it as the critical path — ahead of caption logic.

---

## Critical-path dependency (confirm in the THI repo FIRST)

The engine computes **change over time**. That is impossible if the ingest overwrites state each
run. So before any engine code, Claude Code confirms in the THI **site** repo:

> **Does the ingest RETAIN HISTORY** — enough per-ZIP / per-county history to compute
> week-over-week and month-over-month deltas per metric?

- **If yes:** point the engine at it.
- **If no:** the first build task is adding history retention to THI's ingest (append snapshots,
  don't overwrite). This is a THI-repo change → 🟡 + cross-repo → **surface to owner before
  editing** (harness meta-rule 1). Cheapest form: each ingest run appends a dated snapshot row
  per area per metric to a committed JSON/NDJSON or a D1 table. History depth needed: enough for
  a rolling baseline (≥ 8–12 weeks ideal; 4 minimum to compute *any* delta).

Nothing downstream works until this is settled. It is the true first dependency.

## What the engine computes

For **every metric × every covered area** (ZIP and county), each run:

### 1. Deltas (change, not level)
- `wow` = latest vs. 1 week ago
- `mom` = latest vs. ~4 weeks ago
- `vs_baseline` = latest vs. the area's own rolling median (its normal)
- `vs_neighbors` = this area's move vs. the median move of adjacent areas this period
- `crossed[]` = any named threshold crossed this period (see below)

The interesting thing is almost never the value — it's the **velocity, the rank, and the break
from normal.** Levels are context; deltas are stories.

### 2. Ranking
Within each metric, across all covered areas, sort by rate-of-change and mark the extremes:
`#1 fastest riser`, `biggest faller`, `biggest neighbor-divergence`. Only extremes are headlines.

### 3. The surprise score (this is what guarantees the headline)
Every candidate story gets a scalar `surprise_score`. The caption call receives only the
top-ranked stories. **You guarantee the best available headline by scoring every candidate, not
by writing better copy.** Recommended formula (tune weights against real output; they're config,
not gospel):

```
surprise_score =
    w_mag        * normalized_magnitude        # size of move vs. this metric's normal weekly noise
  + w_rank       * extremity_rank              # is it #1 in the coverage area, or 14th?
  + w_neighbor   * neighbor_divergence         # spiking while neighbors are flat = very interesting
  + w_history    * self_deviation              # abnormal FOR THIS PLACE (z-score vs its own baseline)
  + w_threshold  * threshold_crossed           # crossed a behavior-changing line (binary-ish, high weight)
  + w_money      * money_metric_bonus          # cost/appraisal/insurance weighted above weather-only
  + w_coverage   * audience_coverage           # do we have followers/traffic in this area?
  + w_fresh      * freshness                    # recent > stale
```

Suggested starting weights (money-tilted, per the arousal hierarchy):
`w_mag .20, w_rank .15, w_neighbor .20, w_history .15, w_threshold .15, w_money .10 (multiplier
on cost/appraisal/insurance), w_coverage .10, w_fresh .05` — normalize inputs to 0–1 first.

**Threshold crossings** (high weight — they're inherently story-shaped): entered a higher drought
stage; roof-age × hail exposure crossed the insurance-risk line; appraisal crossed a round-number
mark; energy-cost estimate crossed a seasonal high; grid-stress crossed brownout-risk band. Keep
the crossing list in config so it's tunable per metric.

### 4. The `why` string (editorial gold, generated by code)
For each scored story, emit a plain-language justification of *why it scored high* —
e.g. `"+2 drought stages in 3 wks · #1 in Austin metro · neighbors flat"`. This does triple duty:
it's the human's sanity check, it's the caption's headline justification (hand it to the model as
context), and it's the audit trail the validator uses to confirm the claim traces to data.

## Blind-spot suppression (so the score doesn't crown a dud)

Pure math will occasionally rank a non-story #1. Guard against three:

- **Data glitches:** sensor spikes, revised figures, single-run outliers with no corroborating
  trend → flag if a move reverses next run or has no supporting neighbor/history context.
- **Big-but-boring:** a move that hits everyone equally (county-wide reassessment, metro-wide heat)
  is a large number with *zero surprise* — low `neighbor_divergence` and low `self_deviation`
  should already suppress it, but assert it explicitly.
- **Repeat stories:** an area that was the headline recently shouldn't headline again on the same
  metric unless it accelerated. Dedup against the D5 story-history (ties into the autoposter's
  dedup gate).

Suppressed candidates are dropped from `stories[]` before the caption call ever sees them.

---

## Quiet-week fallback (protects the brand on slow data)

"Most interesting headline **possible**" is bounded by the data. Some weeks nothing moved. The
disciplined response is **NOT to manufacture drama** — that's the alarmist scam-tell the whole
brand refuses. Instead:

```
if max(surprise_score across all stories) < QUIET_THRESHOLD:
    week_mode = "evergreen"
```

In evergreen mode the week pivots to a non-timely angle from a pre-written bank: a "know your
baseline" explainer, a seasonal Pinterest checklist, a "how to read your {metric}" guide. The
loud Movers/Verdict/Wager formats are reserved for weeks the data earns them. The score doesn't
just pick the headline — **it tells you honestly when there isn't one.** That honesty is a
brand-credibility asset, not a failure. Build this branch from day one.

## The `social-feed.json` contract (updated — this supersedes the earlier one-artifact note)

The artifact now carries **history-derived analysis**, not just current levels. Two sections:

```json
{
  "generated_at": "2026-05-14T06:00:00Z",
  "coverage": ["austin_metro", "san_antonio_metro"],
  "week_mode": "live",                     // "live" | "evergreen"  (set by quiet-week check)
  "areas": [
    {
      "id": "78745", "type": "zip", "county": "Travis",
      "metrics": {
        "drought_stage": {
          "value": 3, "wow": +2, "mom": +2, "vs_baseline": +1.8,
          "vs_neighbors": +2.0, "crossed": ["entered_stage_3"],
          "source": "US Drought Monitor", "as_of": "2026-05-13"
        }
        // ... hail_window, energy_cost_est, grid_stress, permit_signal,
        //     appraisal_change (GATED until CAD ingest lands), insurance_trend
      }
    }
  ],
  "stories": [                              // PRE-RANKED, surprise-scored. Caption call reads THIS.
    {
      "rank": 1,
      "area_id": "78745", "county": "Travis",
      "metric": "drought_stage",
      "angle": "warning",                   // reveal | verdict | wager | warning (engine suggests)
      "surprise_score": 0.87,
      "why": "+2 drought stages in 3 wks · #1 in Austin metro · neighbors flat",
      "figure": "+2 stages (now Stage 3)",  // the exact string the caption may use, verbatim
      "source": "US Drought Monitor", "as_of": "2026-05-13"
    }
    // rank 2..N feed the Movers segments + the Wager
  ]
}
```

Contract rules:
- Every `metrics.*` and every `stories[].figure` carries its own `source` + `as_of`. No exceptions.
- The caption call consumes **`stories[]` only** — never raw `areas[]`. This keeps the model's job
  to "voice the pre-selected winner," keeps token use at one call, and keeps every numeral in
  output traceable to a `stories[]` entry (the validator's G1 cross-check runs against this).
- `appraisal_change` / `insurance_trend` money metrics are **absent** (not null, not placeholder)
  until their ingest lands — validator G6 means angles needing them simply don't generate.
- `week_mode: "evergreen"` tells the runner to switch to the fallback bank for that week.

## Where this plugs into the autoposter's 21 steps
- Runs as part of **step 8 (prove the data source)** and becomes a fixed pre-generation stage.
- Its `stories[]` output is the input to **step 5/11 (caption generation)** — the one model call.
- Its `why` strings + `source`/`as_of` are what **VALIDATOR.md G1–G3** check output against.
- Its `week_mode` gates the rotation (`ROTATION.md`) between live and evergreen formats.
- Its dedup against story-history uses the same **D5 breadcrumb** the posting dedup uses.

## Build order (this file's slice)
1. Confirm/establish history retention in THI ingest (🟡 cross-repo — surface first).
2. Delta computation + rolling baseline per metric (🟢, unit-tested against fixtures).
3. Surprise score + ranking (🟢). Tune weights on real historical data before trusting it.
4. `why` string generation + blind-spot suppression (🟢).
5. Quiet-week check + evergreen fallback bank (🟢 + a little content authoring).
6. Emit the `social-feed.json` contract above; hand `stories[]` to the caption call.
Do all of this BEFORE caption generation — a great caption on a dull story still fails.
